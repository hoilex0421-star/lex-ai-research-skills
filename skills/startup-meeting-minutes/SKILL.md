# 初创/专家交流会议纪要

把会议转写（txt/docx）、会后速记、会前调研整理成可上报、可转发的会议纪要。读者是部门领导和项目组专家，用途是技术合作判断和下一代（n+3 代际）算力负载洞察。

## 一、输入与开工

1. 读完整份转写，不能只读前半段。转写里的人名、公司名常有错字，无法确认的保留原样，交付时列为待核实。
2. 用户的会后速记和手动修改版本，优先级高于转写。用户给出的数字和口径（推理时延、训练周期、是否闭源等）直接采用，不要用转写覆盖。
3. 会议信息（时间、地点、与会人员、会议主题）以用户提供的为准。用户没给时留占位，不要编造我方参会人。
4. 参考格式文件只参考版式，不搬内容。
5. 纪要只在内部流转。若要放进公开仓库作为样例，先脱敏：公司、人员、产品名换成代号，融资和团队背景删掉，具体数字改为量级或区间。

## 二、固定结构

```
□绝密 □机密 □秘密 ■内部公开
会议时间：YYYY年M月D日（周X）HH:MM–HH:MM
会议地点：
与会人员：
<对方公司>：姓名（职务）、…
我方：姓名、…
会议主题：面向<目标代际>的……负载洞察与技术合作讨论

一、交流关键信息
1. 交流目标：一句话写清评估什么、获取什么判断，作为目标代际的负载输入
2. 核心结论：3–5 条，每条写成“加粗标签：结论 + 关键数字”
   常用标签：路线 / 模型 / 负载特征 / 数据 / 合作
3. 合作方案讨论：对方现状、顾虑、意愿与切入点

二、交流纪要
### N. <主题>：<带判断的短语>（如“数据闭环构成相对优势”）
结论：一句话（放在结论框里）
1. 要点（必要时加二级 bullet）
…
（负载相关参数集中成一张表：项目 | 当前情况 | 备注，覆盖模型规模、训练、训练加速、推理、预测窗口等）
…
### 下一步计划
1. 行动项（不写“- 我方”这类责任人标注）
```

推荐的小节顺序：
1. 公司定位与团队融资
2. 模型架构与机制
3. 规模、训练与推理负载（用表格）
4. 数据
5. 硬件
6. 技术路线判断（分层、Harness 等）
7. 算力诉求与合作
8. 下一步计划

每节 3–6 条，宁少勿碎。

## 三、写作规则

1. **正文只记对方。** 不写“我方介绍”“我方补充”“我方判断”，也不写我方产品的推介。双方讨论得出的判断，写成不带归属的客观句。
2. **主语默认是对方。** 不写“对方认为”“对方判断”“对方认同”，直接写“认为……”“判断……”。避免带评价色彩的说法，例如“从未试过”改成“目前还未试过”。
3. **判断只放在核心结论里。** 正文写事实和对方观点，不加“这是下一代需要重点关注的点”之类的点评。对我方的启示（如“有优化空间”）只在核心结论中简短出现。
4. **不写负面评价和口语。**
    - 不转述对方对同行、业内工作的贬低（如“方向跑偏”“刷榜”），只保留建设性观点。
    - 不用口语比喻，不用引号做强调。
5. **数字精确，可以追溯。**
    - 写清版本（v0.5 / V1）。
    - 规模写成“～20B”。
    - 区分后训练周期和预训练周期。
    - 注明模型开源还是闭源。
    - 口径冲突时不要自行取舍，先问用户。
6. **用团队术语。** 例如团队约定的代际代号、System 1 / System 2（sys1 / sys2）、端边侧、MoT、WAM / ACWM。写法保持团队习惯。
7. **保留待核实标记。** 与公开资料不一致的数字写成“N 个（公开资料为 M 个，待核实）”。
8. **句子短，结论先行。** 每个小节的第一句就是判断。

## 四、交付形式

- 默认在可协作的文档里起草，方便用户直接改；逐节填写。
- 用户要发邮件或用 Outlook 时，把纪要写成 JSON（格式见 `assets/example-minutes.json`），然后运行：

  ```bash
  python3 scripts/build_email.py minutes.json --out ./out
  ```

  脚本会生成两份文件：
  - `.eml`：带 `X-Unsent: 1` 头，双击后在 Outlook 中以草稿打开，补上收件人即可发送。
  - `_邮件正文.html`：在浏览器打开后全选复制，粘贴到邮件正文。
- 邮件样式（脚本已内置）：
  - 所有样式内联，用 table 布局，不用 class 或 flex。
  - 字体：微软雅黑；正文 14px。
  - 一级标题：深红 #A11D21，下方加深红线。
  - 结论框：淡灰底 #F2F2F2，左侧加灰色边条 #A6A6A6，文字深红加粗。**不要用粉红色。**
  - 表格：表头 #F1EFEA，边框 #D9D5CC。
- 生成后用浏览器截图检查渲染效果，再交付。

## 五、交付前自查

1. 核心结论里的数字（时延、参数量、预测窗口、数据规模）与正文、表格一致。
2. 正文中没有“我方”“对方认为”，没有负面评价，也没有正文点评。
3. 列出仍需用户确认的点：转写里的人名和公司名、与公开资料冲突的数字、口径冲突。回复里用一两句说清楚，不要长篇复述纪要内容。
